# ScoreBook 仓库初始化、授权与持续演进设计

本文提出下一阶段的产品设计，尚未实现所列工具或创建远端仓库。现有十一章参考手册作为内容基线保留；仓库能力围绕它建设。本地文件是否已提交、远端权限是否已落实和 Stage 是否已加载，分别核验。

2026-10-19，用户确认先维持本设计方向，转入 Stage 设计。本次确认覆盖 GitLab 优先、产品模板与企业多仓分离、按读者授权、初始化核验、保留企业定制的升级和独立知识贡献流程；具体 schema、命令接口、平台最低版本和实施细节仍为待细化提案。方向确认不代表工具已实现、产品已发布或企业制度已生效。

2026-10-27，用户确认 OrchestraCorp 四个产品仓均采用 MIT 并公开。ScoreBook 的产品许可见 [LICENSE](../LICENSE)，可独立复制的参考公司包含[同一许可证](../reference-company/LICENSE)。该决定适用于产品模板的分发，不改变企业实例的私有托管、资料授权和生效边界。

## 1. 本轮设计结论

ScoreBook 应交付“参考内容＋企业仓库生成规则＋GitLab 初始化与检查工具＋持续演进方法”。产品自身维护一个 Git 仓库；一家企业的逻辑 ScoreBook 可以由多个独立私有仓组成。

首版优先支持企业自托管 GitLab。GitLab 地址、版本、许可证、实例策略和 API 能力都由接入检查确定，不写死某个实例。GitHub 用于公开产品模板，不进入首版企业数据初始化与授权流程；不能将企业数据、远端配置或历史提交自动推向产品分发渠道。

按实际读者集合分仓，而不是按参考目录机械建仓。十个参考部门可以合并，也可以按需要形成多个不同读者范围的仓库。只做一次复制无法满足后续的权限核验、Git 使用和模板升级，因而需要保留可追踪的初始化配置与来源基线。

## 2. 产品仓与企业仓各自保存什么

建议产品仓逐步形成以下结构。`docs/` 已建立，其他新增目录及工具均为拟建；现有参考内容不因本方案自动迁移或改写。

```text
ScoreBook/                         产品维护者的一个 Git 仓库
├── AGENT.md / AGENTS.md            产品维护入口
├── README.md / architecture.md
├── reference-company/             参考手册、部门、岗位和知识模板的内容源
├── examples/                      外部参考、许可和来源记录
├── docs/                          采用、权限、Git 协作、升级与恢复说明
├── blueprints/                    组织选择、内容路由与授权配置样例（拟建）
├── repository-packs/              各类企业仓的 AGENT、MR 和 CI 模板（拟建）
├── schemas/                       初始化配置、lock、内容与发布清单格式（拟建）
├── tooling/                       内容生成、校验、升级及 GitLab 适配（拟建）
├── tests/                         生成、权限、升级与恢复测试（拟建）
├── LICENSE                        MIT 产品许可（已建立）
└── CHANGELOG.md                   发布说明（拟建）
```

`reference-company/` 保持组织内容的主要维护位置。`repository-packs/` 只保存仓库运行所需的包装文件，不复制一套手册正文。`blueprints/` 描述选哪些内容、放到哪里、谁能读取与审阅，不保存真实企业的配置。

企业仓拥有自己的提交历史和版本。初始化从选定产品版本提取内容后创建新 Git 仓库，不将产品仓的完整历史或外层维护指令复制进企业。企业实例也不默认成为产品仓的 fork。

产品模板、生成规则和工具应分别标识版本；一次产品发布记录它们的兼容组合及精确提交。发布不能只靠一个可能移动的标签，需同时记录提交和内容摘要。

## 3. 企业仓库拓扑

以下是逻辑示意，不是已经创建的组织、项目或人员安排。

```text
企业 GitLab 私有命名空间
├── shared/
│   └── scorebook-core              公司通用制度、岗位和协作接口、共享知识
├── departments/
│   ├── engineering/scorebook       工程内部知识，按需创建
│   └── customer-success/scorebook  客户成功内部知识，按需创建
├── restricted/
│   └── <access-domain>/scorebook   指定读者的正式材料或受限知识，按需创建
├── initiatives/
│   └── <initiative>/scorebook      独立跨部门参与范围的长期知识，按需创建
└── administration/
    └── scorebook-control           初始化配置、完整权限拓扑和发布协调记录
```

`restricted/` 只是组织名称，不产生权限。顶层及中间 group 只放确实应继承到全部下级的管理主体；全员读权限授予 `shared/` 或具体共享项目。GitLab 父组成员权限会向下继承，不能靠子组降低。因此，已有父组成员过宽时，先调整成员模型或采用独立顶级组，不能在原树下宣称已隔离。平台机制见文末来源 [1]。

所有企业项目默认使用 GitLab 的 **Private** 可见性；公司内部共享通过成员授权实现，不采用平台 `Internal` 可见性。管理和受限仓可以落在另一命名空间，只要配置与索引遵守同一读者边界。

`scorebook-control` 面向初始化与发布管理者，不要求员工或每个 Maestro 都能读取。它保存受限的完整拓扑；共享仓仅列出允许共享的仓库信息。对于小团队，控制配置可放在另一个已有受限管理仓，不必固定多建一个项目。

本地企业工作区是若干同级 checkout 的容器，自身不建立聚合 `.git`；默认不使用 submodule。工具按有效授权仅拉取相关仓库，也不要求普通员工拥有完整控制配置。

首版支持两个布局：`shared` 将读者完全相同的非敏感内容放在一个共享仓；`partitioned` 按实际读者分仓。受限资料在两个布局下都需要独立权限域，不能先放共享仓再承诺以后移动即可保密。删除当前文件不会清除历史提交；分类升级另走历史暴露评估与迁移处理，见来源 [3]。

## 4. 参考内容怎样生成企业仓库

生成规则为每个源文件分配稳定 `template_id`，记录目标仓库、目标路径和选用条件。稳定 ID 不依赖文件名或部门名；所有路径变动保留映射。

| 来源内容 | 默认目标 | 生成时处理 |
|---|---|---|
| 公司 AGENT、手册、治理、组织和跨部门方法 | `scorebook-core` | 使用企业入口；填写允许进入共享仓的参数，保留企业待确认项 |
| 部门使命、职责、岗位目录、协作接口 | `scorebook-core/departments/` | 默认保留可共享职责，方便跨部门找人和确认接口 |
| `departments/<department>/knowledge/` | 相应部门仓的 `knowledge/`，或同读者的共享仓 | 按选定布局路由；重新生成目录入口和有效引用 |
| 共享知识模板、虚构示例 | `scorebook-core/knowledge/` | 样例始终保留虚构和无政策效力标记 |
| 企业受限知识 | 对应权限域仓或专业业务系统 | 初始化只建立空结构与规则，不生成真实业务数据 |
| 产品 `examples/` 与产品维护文件 | 不默认进入企业 | 企业明确采用的材料另经许可、来源和内容审阅 |

拆仓必须重写内部链接。企业 core 的 `AGENT.md` 继续作为公司入口；每个部门或受限仓都由对应 pack 生成自己的根 `AGENT.md`，说明本仓使命、可读范围、审阅方式和引用规则。它不依赖产品仓父级文件，也不暗示其他企业仓已可读取。

跨仓引用使用 `repository_id + content_id + commit`，由获授权的工作台或检查器解析；普通相对路径只用于本仓。需要本地规则副本时，生成有明确来源版本的批准摘录，不创建第二份可独立修改的权威正文。受限仓名称、链接、摘要及来源对象同样不能泄漏到共享索引。

配置检查要求每个选中文件有且只有一个权威目标；同一原则的引用或批准摘录要标明派生关系。未知文件、重复目标、未分类内容、越界路径和指向源目录外的符号链接均不能静默跳过。

## 5. 初始化配置与工具契约

初始化需要四类输入，均有 schema 版本：

| 输入 | 内容与存放位置 |
|---|---|
| 产品版本 | 精确提交、发布摘要、内容目录和兼容工具版本；来自受信任的产品发布或离线包 |
| 企业蓝图 | 选用部门、布局、内容路由、仓库用途与读者策略；存于企业受限控制配置 |
| GitLab 绑定 | 实例地址、目标 namespace/project ID、成员或成员组引用、审阅角色；不得回写产品模板 |
| 认证引用 | 操作系统凭据管理、受控运行环境或交互认证；配置只记录引用，不保存 token |

工具核心负责内容与 Git 规则，GitLab adapter 负责平台 API。首版只实现 GitLab adapter，但避免把 API 参数散进内容渲染与升级逻辑。企业可在无网络环境使用固定离线产品包生成本地仓。

建议首版提供以下目标接口，**这些命令尚未实现**：

```text
scorebook plan --config <enterprise-config>
scorebook apply --plan <plan-file>
scorebook verify --config <enterprise-config>
scorebook upgrade plan --to <product-release>
```

### 5.1 plan：生成可审阅的初始化计划

读取配置、产品内容及可访问的 GitLab 当前设置，不创建远端资源。计划记录输入摘要、时间、目标仓列表、每个文件的路由、预计成员与继承来源、默认分支规则、所需动作、平台能力和阻塞项。

本地预览写入明确指定的临时输出位置。计划、预览和日志与企业配置同级保护，不上传产品仓，也不包含凭据。未完成身份或权限核验时明确显示未知状态。

### 5.2 apply：执行选定计划

执行前重查计划摘要、当前权限和目标是否变化，不能复用已经过期的权限快照。已有仓库或非空目录默认拒绝覆盖；接管现有仓库必须另有显式流程。

本地阶段先生成临时目录、校验链接与元数据，再创建独立 Git 历史和初始化提交。Git 作者身份使用操作者明确配置，不替用户猜测身份或设置全局 Git 配置。

远端阶段创建只对初始化管理主体开放的 Private 项目，写入首次主分支，随后配置保护分支、CI 和审阅要求。先完成本批项目的保护与继承关系核验，再按计划发放普通成员权限，并复核实际授权结果。首次空仓建立主分支是记录在案的 bootstrap 步骤；进入协作状态后不再直接推送主分支。允许复用的只有计划明确认定属于本次操作的资源，不凭同名项目推断归属。

首版提供本地生成和 GitLab 创建、绑定、权限检查；托管能力不足或操作者无权执行时，输出明确的手工配置项，再经 `verify` 核验。手工模式不是自动判定通过，也不得绕过企业要求的强制权限规则。

每步保存不含凭据的执行回执、创建资源 ID 和状态，支持失败后重试。默认不删除远端仓、不重写已有历史；恢复时重查已完成步骤。授权前失败时不发放普通成员权限；授权阶段中途失败时立即停止后续授权，按日志核验并撤销本次新增且可安全确认归属的授权与邀请，不撤销企业已有授权。恢复未完成或继承权限无法收敛时，记录实际可见范围并标记 `access-verification-failed`，不能声称只剩管理主体可见，也不能将整个工作区标为就绪。

### 5.3 verify：验证实际结果

核验文件完整性、仓库入口、链接、来源锁定、Git 状态、远端项目可见性、直接与继承成员、共享组、默认分支保护、匹配通配规则、CI 状态和审阅能力。预期配置存在于 YAML 不代表平台实际设置正确。

至少区分 `content-ready`、`gitlab-access-verified`、`review-controls-verified` 和 `stage-not-connected`；报告每项证据、核验时间和未知项。权限证据过期、GitLab 不可达或能力未知时，不输出整体“已安全部署”。

## 6. 企业日常 Git 使用与授权

默认流程为“拉取准确基线 → 工作分支 → 修改和检查 → MR → 责任岗位审阅 → 有权的人合并 → 发布内容版本”。Maestro 可在有效授权内编辑、提交和开 MR；默认没有 Maintainer/Owner，也不批准自身治理变更。

| 主体或对象 | 默认权限与职责 |
|---|---|
| 公司成员 | 读取公司共享仓；需要修改时获得相应项目的开发权限 |
| 部门成员 | 按职责读取或修改部门仓；不因属于公司就自动读取全部部门原文 |
| 跨部门协作者 | 获取特定仓库的限期角色，或接收获准披露的交付物；GitLab 项目权限不能包装为任务级文件权限 |
| 外部会计等第三方 | 只进入指定项目或独立权限域，不加入会继承全企业读取权的父组 |
| 领域 Maestro | 每项目或权限域单独身份和认证，通常至多 Developer；初始化管理凭据不用于日常 Agent |
| 主分支 | 协作启用后禁止直接推送、禁止 force push；由有权人经 MR 合并 |
| CI、runner、工件及检索 | 与源数据权限相容；受限仓不向共享 runner、工件、缓存或聚合索引输出原文 |

仓库 pack 提供 README、AGENT、MR 模板、检查脚本与 CI 配置、必要的 CODEOWNERS 和变更说明；每一项只有对应检查真正可运行时才在初始化报告中标为启用。

GitLab Code Owner 强制审批有版本和许可证条件；CODEOWNERS 文件本身不承担读取隔离，也不保证审批已经强制执行。GitLab 多条匹配保护规则可能产生更宽的推送、合并或 force push 权限，检查器必须计算或读取有效结果，不能只检查 `main` 一条配置。见来源 [2]。

Free 环境可采用“开发者提交、指定人类 Maintainer 合并”的职责分离，但这不等价于平台已强制任意两名独立人员批准。企业要求机器强制的多人审批而平台不具备时，计划应阻塞该要求，并列出可选择的部署能力或明确批准的人工流程，不静默降低标准。

项目访问 token 可作为日常 Agent 的认证方式，但创建者、角色、scope、期限和撤销分别核验；一个项目的 token 不适合作为全企业初始化凭据。官方文档还说明其内部用户语义可能使 `Internal` 项目扩大可见范围，因此本方案统一默认 Private，见来源 [4]。

Git 用于正式内容与审阅，不恢复 `people/*/tasks` 等第二套实时任务库。任务承诺、当前权限、离岗撤销和运行状态继续由 Stage 或相应业务系统承载；GitLab 自身的访问权限仍须实际授予和撤销，Stage 的记录不能代替平台动作。

## 7. 模板升级与企业定制

每仓生成 `.scorebook/template-lock.yaml`，保存产品精确版本、生成器与路由版本、选用组件、稳定模板 ID、目标路径、源内容摘要、管理方式与最近采用记录。另保存按本仓权限可读的精确生成基线，或经完整性验证且可长期获取的等价快照。只有摘要不足以重建三方合并所需内容。

基线必须是替换企业变量、选择组件、拆仓和改写引用之后，曾实际生成的版本；不能用产品仓原始文件代替。基线与本仓数据使用同样权限，不能在共享仓缓存全部受限仓的参数或内容。

升级先生成分支、差异与 MR，以三个输入比较：

1. 上次该仓采用的模板生成基线。
2. 当前企业文件，包括企业自己的修改。
3. 新产品版本按目标配置生成的模板内容。

稳定 ID 用于识别改名和移动；文本三方合并只能辅助处理内容，不能代替职责或制度判断。上游删除、本地新增重名、双方修改、schema 迁移和权限域变动都需要显式处理。未经确认不自动删除企业内容，也不从宽权限仓复制历史到受限仓后宣称完成保密迁移。

区分 `managed`、`adapted`、`company-owned` 和 `pinned`：可追踪生成内容、保留企业偏离的内容、企业自有内容、固定旧基线的内容。部分采纳逐文件记录，不能用一个新版本号假称全部升级。新的上游生成基线与最终合并后的企业文件分别保存；若把企业个性化文件当成上游基线，下次升级会丢失偏离信息。

企业用模板填写产生的新知识、决策和验收记录只保存 `content_id` 及来源模板关系，默认属于 `company-owned`，不进入模板自动升级清单。模板格式更新另提出迁移建议，不能改写已经批准的事实。

## 8. 多仓内容发布与 Stage 接入

独立知识修改可以在本仓独立审阅和发布。只有跨仓约束或共同制度变更需要企业发布清单，锁定各参与仓的精确 commit、内容 ID、依赖和兼容条件。

完整清单保存在授权控制域；共享仓只保存允许共享的子清单和发布信息。各仓提交均已审阅、可取得并校验之前，不能把半完成组合标为可激活版本。Git 不提供本方案所需的跨仓原子事务，首版用可重试的准备状态和明确发布记录协调。

内容发布与运行激活分开：首版可在没有 Stage 时生成和使用 Git 内容，但必须标记未连接运行系统。未来 Stage 按批准清单校验、加载并记录实际成功、失败和当前有效版本；未实现对应协议前不承诺整体运行切换。

内容回退以新的 revert 提交或新的企业发布保留历史，运行回滚由 Stage 另行执行。旧模板、旧 commit 或旧发布永远不能恢复 Stage 已撤销的授权；也不能靠回退文档绕过 GitLab 当前权限。

## 9. 知识积累与产品持续演进

企业内演进路径为“工作证据 → 获授权的整理候选 → 责任岗位审阅 → 本企业知识发布 → 复用反馈与复核”。默认记录稳定内容 ID、责任岗位、来源、分类、适用范围、验证依据、版本、取代关系和复核条件；各仓只处理有权接触的证据。

部门经验提升为公司共享知识时，另建允许共享的新内容或经审阅的摘录；完整来源映射留在原权限域，共享文本不带受限事实。此过程不靠把受限分支直接合并进共享仓完成。

企业知识反馈产品模板走独立贡献流程：企业明确同意披露与贡献范围，形成通用候选，检查真实数据、内部链接和许可，再从干净产品工作副本创建 MR。不得自动推送企业仓、历史、远端设置或原始证据；扫描不能代替披露授权。对外来源只保留获准披露的信息，完整映射仍由企业保存。

产品维护者审阅通用性和来源后，更新参考手册、部门结构、模板或生成规则，发布新产品版本。企业自行选择是否升级，形成“产品默认基线 → 企业实践 → 经授权的通用改进 → 新基线”的循环。

## 10. 首版实施范围与验收

本轮形成设计，不把下列拟建能力标成已经完成。建议将现有手册内容基线和后续仓库工具能力分别发布，避免“手册定稿”被理解成“初始化工具已可用”。

| 阶段 | 实现内容 | 完成条件 |
|---|---|---|
| A：产品仓基础 | 为产品自身建立独立 Git 历史、许可决定、变更记录和版本基线 | 来源、发布边界与维护流程明确；不创建企业真实数据 |
| B：本地初始化 | schema、两种布局、内容路由、仓库 pack、来源锁定与生成基线 | 干净目录能生成多个独立 Git 仓；链接正确、无文件遗漏和权限域混装；重跑不会覆盖已有文件 |
| C：GitLab 接入 | 认证与能力检测、计划、私有项目创建或绑定、保护和成员核验 | 继承过宽可阻塞；成员发放前完成配置；失败可恢复；未知状态不会伪装通过 |
| D：协作与升级 | MR/CI 使用说明、三方升级、偏离记录、发布清单与知识贡献规则 | 用户定制和自有知识在升级中保留；冲突显式显示；可验证一次跨仓准备失败后的重试 |

首版不建设 GitHub 企业适配、任意跨仓知识自动搬迁、自动向产品回流、全局无限权限 Maestro 或分布式运行激活。为后续平台保留 adapter 边界，不预先实现通用权限平台。

初始化程序测试覆盖越界路径、非空目录、重复 apply、失败恢复、授权发放中途失败、父组继承、通配分支放宽、平台能力缺失、部分升级、上游改名删除、自有知识保护及受限索引泄漏。测试在虚构数据和专用测试项目中执行，不修改真实企业权限来试错。
