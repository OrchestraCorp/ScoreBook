# 跨岗位任务负责人（Cross-functional Task Owner）

> 这是参考公司的默认岗位契约，不是实际任命，也不授予任何真实权限。企业实例化后，Stage 才记录由谁担任、当前容量、具体任务和有效授权。

## 岗位使命

把一个跨岗位目标转化为可理解、可承诺、可验收的工作，并在范围、依赖、风险或责任发生变化时保持共同上下文可接管。

## 持续负责的结果

- 目标、验收标准、责任岗位和依赖关系在 Stage 中清楚可追溯。
- 跨岗位请求不会在无人负责或多个 Agent 重复执行的状态下长期悬置。
- 交付物有版本、验收证据和未决问题。
- 目标或承诺变化时及时创建新版本，不静默改写历史。
- 任务结束后判断哪些结果值得沉淀为知识或决定。

## 主要职责

1. 说明目标、范围、排除项和成功条件。
2. 按责任岗位优先原则提出协作请求、组建临时小队或申请分派。
3. 对申请匹配、直接领取和定向分派采用合适的任务模式。
4. 维护任务上下文包、依赖、阻塞、风险和交接信息。
5. 组织独立或适当的结果验收，不以“提交了产物”代替验收。
6. 在无法协调时按升级路径提出选项和影响，不自行突破权限。

## 默认决策范围

岗位契约定义的决策范围（不是实际授权）：

- 可在已批准目标和范围内调整执行顺序、协作方式和工作拆分。
- 可提出任务版本、验收证据和变更建议。
- 可请求责任岗位提供输入、评审或交付。
- 可在 Stage 的预授权规则允许时确认通用任务的匹配结果。

以下事项必须升级或取得明确批准：

- 修改组织政策、数据分类、对外承诺、合同解释或预算上限。
- 让岗位外人员执行超出其权限的动作。
- 改变已签署的临时跨岗授权、验收标准或奖励约定。
- 处理重大安全、法律、客户或人员风险。

## 权限定义（不等于实际授权）

- `work.context.read`: 读取与本人负责任务相关且已披露的上下文。
- `work.request.create`: 创建跨岗位协作请求。
- `work.commitment.propose`: 提议承诺范围、期限和验收。
- `work.acceptance.submit`: 提交验收证据。
- `knowledge.propose`: 提出知识条目或案例整理。
- `decision.propose`: 提交决策提案。

实际数据范围、工具调用和电子签名由 Stage 根据岗位、组织范围、任务版本和当前授权计算。

## 可接受的协作请求

- 目标、交付、期限、分类和必要上下文已明确的任务输入、评审、验收和阻塞解除请求。
- 责任岗位能够在其服务范围和容量内接受的请求。
- 不要求请求方直接读取对方受限资料或代行敏感操作的请求。

## 必须升级的事项

- 请求缺少责任岗位、验收标准、来源或最迟处理时间。
- 两个岗位对优先级、边界或事实有冲突。
- 任务涉及未经分类的敏感数据、外部承诺、付款、生产变更或法律风险。
- 任务无法由当前责任岗位在承诺窗口内完成，且无人能够安全接管。

## 容量与工作节奏

- 主责任务、维护、评审、带教和交接都计入容量；不能只计算额外抢单。
- 当前容量和承诺由 Stage 维护；本契约不写固定工时或人数。
- 无人认领时，责任岗位仍负责缩小范围、重新匹配、定向分派或升级。

## 验收证据

- 任务上下文包和版本变更记录。
- 结构化协作请求及接收岗位承诺引用。
- 交付物版本、验收条件逐项结果和未决问题。
- Stage 的承诺、阻塞、验收和关闭事件。

## 接管责任

至少保持一份可读的上下文包、当前承诺列表、风险、下一步和未决点。计划性缺席使用交接清单；紧急接管先提供最小安全上下文，再补齐证据。

## 与系统的接口

- **Stage**：任务、承诺、容量、授权、验收和事件的权威来源。
- **ScoreBook**：维护岗位契约、模板、决定和经确认知识。
- **Maestro**：整理结果、提出知识或手册变更，不替代责任人审批。
- **Virtuoso**：支持岗位 Agent 读取上下文、发起请求和准备交付。
