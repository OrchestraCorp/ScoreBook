# OrchestraCorp 默认组织操作手册：编写纲要

> 本文保留手册的编写纲要与验收目标。截至 2026-10-19，十一章参考初稿已经建立，当前正文以[手册入口](README.md)为准。以下章节主张和示例属于建议的默认基线，企业采纳、发布并建立实际责任安排后，才成为该企业采用的制度。

## 一、写作目标

写出一套有明确组织观、覆盖常规公司事务、可供直接审阅和采用的默认操作手册。软件内核保持通用，手册提供具体默认选择；企业从完整基线开始调整，不从空表开始重新发明组织。

手册描述的是一个参考组织的运作方式，不绑定已有人员、固定部门、经营者姓名或特定行业。岗位可以兼任，专业支持可以内部提供或外部委托；重要责任需要落到具体人，不能只留一个虚构部门名称。

不把任何组织范式宣称为未经验证的最优制度。默认主张应有目的、适用条件、局限和修改依据，后续用不同企业场景验证。

## 二、三类内容明确标记

| 类型 | 写法 | 示例 |
|---|---|---|
| 默认做法 | 给出完整陈述和推荐选择，供企业整体采纳 | 跨岗位需求优先请求责任岗位协作 |
| 企业必填 | 只填写需要真实背景才能确定的事实与参数 | 公司使命、实际责任人、预算限额、业务系统 |
| 可调整项 | 明确允许怎样改、影响什么以及需要怎样记录 | 决策授权深度、评价周期、任务市场开放范围 |

已有用户共识直接作为参考手册的基线输入；此前仅建议过的机制与数值不借此次成文升级为已确认要求。工资、奖金权重、具体额度及人员安排不凭空编造。

## 四、每章固定写法

1. **目的与适用范围**：这项规则要解决什么问题，适用于哪些工作。
2. **默认约定**：用明确、可以采用的句子描述日常做法。
3. **责任分工**：谁作决定、谁承担结果、谁执行、谁提供专业支持或复核。
4. **自主权与边界**：可以直接做什么，哪些事项需要确认或升级。
5. **记录与系统承载**：需要哪些依据，ScoreBook、Stage、Maestro、Virtuoso 各承担什么。
6. **例外与企业适配**：需要填写哪些参数，怎样申请例外或修订默认做法。
7. **场景示例**：一个正常案例和一个越界、冲突或交接案例。

正文先用员工、管理者和经营者能理解的工作语言，API、数据库字段、状态机和技术实现放在后续规格中。手册不是工程接口文档。

## 五、具体写作示例

以下示例用于体现成文程度，不单独构成生效制度。

### 工作分配与协作：默认约定样例

每项工作都有明确的责任岗位。跨岗位需求优先请求责任岗位协作，由该岗位安排分派、认领或组队；需要原执行者临时代行其他岗位职责时，提出限定范围的申请，由有权的人确认并电子签名后执行。

开放任务同时支持申请后匹配，以及满足条件即可直接领取。通用任务直接领取经 Stage 确认成功后，立即形成正式承诺；申请匹配中的报名只表示意愿。员工 Agent 代为承接时，需要已有有效委托。

承诺说明目标、交付、验收与期限。接受任务不自动扩大数据和动作权限。无人认领的任务仍有责任岗位安排，不能因为进入任务市场就失去组织责任。

岗位主责、维护、值守、评审和带教计入真实工作容量。员工完成岗位主责能够达到相应绩效预期，不以额外抢单作为基本达标条件。具体容量和奖励规则由企业采用时确定。

### 在四个模块中的承载

- **ScoreBook**：保存这项组织约定及其批准版本。
- **Stage**：保存当前任务、资格核验、承诺、容量与交付证据。
- **Virtuoso**：支持员工或其 Agent 发现任务、准备申请、承接和完成工作。
- **Maestro**：从已确认的工作结果中整理经验与修订建议，不凭一次例外自行改变制度。

## 六、与现有目录的关系

手册是人阅读的组织规则正文。其他目录保留不同用途的对象和资料，避免同一条制度各写一份：

以下路径均以当前公司 Repo 的根目录为基准，产品仓中对应 `reference-company/`；实例化后不需要外层目录。

- `governance/`：授权配置、信息分类、规则索引和机器执行映射；引用手册中的规范条目。
- `organization/`：可复用岗位契约与责任模型，实际任职由 Stage 管理。
- `agents/`：Agent 能力、责任与配置定义。
- `knowledge/`：经过验证的操作方法、SOP、Skill 和案例，来源于手册及实际工作。
- `decisions/`：采纳、修订或取代规则的正式决定与依据。
- `repositories/`、`archives/`：来源索引、历史归档与回执。

本手册以 `charter.md` 为统一组织宪章正文。`governance/constitution.template.md` 是保留的起步模板，后续应统一其引用和采用说明，避免企业同时维护两份宪章；保留模板不表示已在任何企业采用或生效。

## 七、默认手册与企业采用

默认手册发布在产品模板中，企业采用一个明确版本，完成必填责任与参数、适用性审阅和必要的内部程序后发布自己的版本。Stage 记录实际采用的版本和生效范围。

企业的偏离写清改变什么、为什么、谁负责和何时复核。产品手册升级不会静默覆盖企业已经采用的规则，企业可以比较差异后再更新。

涉及劳动、人事、数据、签署及行业要求的章节，采用前按实际适用规则复核。本纲要不对具体条款作法律效力承诺。

## 八、编写与验收顺序

以下是原定建设顺序。十一章参考初稿、岗位契约、知识模板及样例已经建立；跨文档一致性、企业采用检查和机器配置映射仍需后续推进。

1. 先完成十一章的完整简版，让参考组织能够被整体理解，而不是只把授权章写到很深。
2. 用客户需求、内部支持、采购、入离职、组织知识和事故接管等场景检查缺口。
3. 统一术语和跨章引用，确保责任、授权、任务、评价与信息边界一致。
4. 区分默认机制、企业必填与可调整项，给出适用边界。
5. 补岗位与文档样例，再建立机器配置映射及 Stage 接口。

一版手册的验收标准：读者能知道应该怎样工作、找谁决定、留下什么依据、遇到例外怎么办；企业无需重写所有制度即可评估采用，同时不会误以为产品文件已经自动成为本公司的生效政策。
